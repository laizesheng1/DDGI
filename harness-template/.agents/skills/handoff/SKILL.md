# Handoff

## 操作模式

- 保存：用户要求 handoff、save state、compact prep、保存状态或准备交接时，更新 `docs/HANDOFF.md`。
- 恢复：用户要求 resume、continue from handoff、从 handoff 恢复或继续上次任务时，读取 `docs/HANDOFF.md` 并从下一步继续。
- 意图不明确时，最多问一个澄清问题；不要自行猜测并写入或删除文件。

## 文件位置

- 当前 handoff 状态：`docs/HANDOFF.md`

保存时如果 `docs/` 不存在，直接创建。`docs/HANDOFF.md` 是当前交接状态文件，不是追加日志。

## 事实核对

保存和恢复时，先核对当前工作区事实，不要只依赖对话记忆。对代码仓库，可参考版本控制状态、相关 diff、分支/提交。

## 保存 Handoff

保存前核对当前工作区事实。

每次保存都更新 `docs/HANDOFF.md`，使其成为一份完整、去重、可直接恢复的当前状态；不要把它写成追加日志。

handoff 内容必须包含：

- 当前目标
- 当前状态
- 重要决策
- 已尝试方案
- 失败尝试 / 死路
- 构建 / 测试 / 验证情况
- 已知阻塞
- 下一步

写作要求：

- 简洁，但要具体。
- 优先写明确的文件路径、命令、错误名、下一步动作。
- 不写泛泛而谈的建议。
- 不复制无关聊天记录。
- 不隐藏失败尝试。
- 如果没有运行 build/test，要明确说明没有运行，而不是假装通过。
- `构建 / 测试 / 验证情况` 只写关键验证（完整回归、定向测试、真实链路、未运行项），不要写重复命令或 artifact 流水账。

建议在文件顶部额外记录更新时间和工作目录；如有版本控制上下文，可记录分支和提交，方便恢复时核对事实。

## 恢复 Handoff

读取 `docs/HANDOFF.md`，再检查其中列出的关键文件和当前工作区事实。

如果 `docs/HANDOFF.md` 缺失、空泛不可用，或与当前工作区事实矛盾，先说明问题；不要凭空编造状态，并以当前工作区事实为准。

恢复后先简短总结：

- 当前目标
- 当前状态
- 关键文件
- 已知阻塞
- 接下来 1 到 3 个动作

除非下一步确实有歧义，否则直接从 `下一步` 继续执行，不要重复已经完成的工作。
